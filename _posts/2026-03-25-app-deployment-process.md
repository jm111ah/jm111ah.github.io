React Native로 앱을 만들 때 **“개발이 끝났다”**와 **“사용자가 스토어에서 받을 수 있다”** 사이에는 꽤 명확한 **배포 프로세스**가 있습니다. 이 글에서는 그 과정을 **앱 배포** 관점에 맞춰 한 번에 정리합니다. (프레임워크는 요즘 많이 쓰는 **Expo** 흐름을 기준으로 설명하고, 백엔드는 **운영 단계에서 병행되는 별도 축**으로만 짚습니다.)

## 1. 무엇을 “배포”하는가

- **스토어에 올리는 것**은 **사용자 기기에 설치되는 앱 패키지**입니다.  
  - iOS: **IPA** 형태로 빌드 후 App Store Connect로 전달  
  - Android: 보통 **AAB**(Google Play 권장)로 빌드 후 Play Console로 전달  
- **API 서버·DB**는 앱 바이너리 안에 들어가지 않습니다. **별도 URL·서비스(Firebase, Supabase, 자체 API 등)** 로 운영하는 것이 일반적입니다.

즉 **앱 배포 프로세스**는 주로 **클라이언트 빌드 → 스토어 업로드 → 메타데이터·심사 → 출시**이고, 백엔드는 **각자의 배포·설정 파이프**를 갖습니다.

## 2. 사전에 준비할 것

| 준비 항목 | 설명 |
|-----------|------|
| **개발자 계정** | Apple Developer Program(유료), Google Play Console(등록비) |
| **앱 식별자** | iOS 번들 ID, Android 패키지명 — 빌드·스토어 등록 시 고정 |
| **버전 규칙** | 사용자에게 보이는 버전과 빌드 번호(스토어 정책에 맞게 증가) |
| **리소스** | 아이콘, 스플래시, 스크린샷, 개인정보 처리 안내 등 스토어용 자료 |

## 3. Expo를 쓰는 경우의 전형적인 흐름

개인·소규모에서 **Expo + EAS(Expo Application Services)** 조합은 흔합니다.

1. **개발 마무리**  
   기능·UI 완성, `app.json` / `app.config` 등에 앱 이름·식별자·권한 설명 반영  

2. **프로덕션 빌드**  
   **EAS Build**로 클라우드에서 iOS/Android **스토어용 빌드** 생성  

3. **스토어에 전달**  
   - **EAS Submit**으로 App Store Connect / Play Console에 업로드하거나  
   - 생성된 산출물을 콘솔에 **수동 업로드**  

4. **스토어 콘솔 작업**  
   설명, 카테고리, 개인정보·권한 문항, 연령 등급 등 **심사/검토용 메타데이터** 작성  

5. **심사·검토**  
   - Apple: 심사(소요 시간은 가변)  
   - Google: 정책 검토(상대적으로 빠른 경우가 많으나 앱마다 다름)  

6. **출시**  
   프로덕션 트랙에 공개, 또는 단계적 롤아웃  

**내부·베타**는 **TestFlight(iOS)**, **Play 내부/클로즈드 테스트**로 먼저 돌리는 경우가 많습니다.

## 4. “순정” React Native(Bare)인 경우

로컬에서 **Xcode**로 iOS 아카이브, **Android Studio / Gradle**로 서명된 릴리스 AAB를 만들고, 이후 단계는 위와 같이 **업로드 → 콘솔 → 심사 → 출시**입니다. 네이티브 설정·서명을 **직접** 맞추는 비중이 큽니다.

## 5. 출시 이후 업데이트

- **네이티브 코드·권한·일부 SDK 변경**이 있으면 **다시 빌드 → 업로드 → 심사(또는 검토)** 를 거치는 경우가 많습니다.  
- **JavaScript·UI만 변경**하는 경우, **Expo EAS Update** 같은 **OTA(Over-the-air)** 로 스토어 심사 없이 번들만 갱신하는 방식도 있으나, **적용 가능 범위와 스토어 정책**을 반드시 확인해야 합니다.

## 6. 백엔드·비용과의 관계 (배포와 분리해서 보기)

- **BaaS**(Firebase, Supabase 등)나 **서버리스 API**, **VPS**는 **앱 스토어 배포와 별개**로 **계정·요금·한도**를 관리합니다.  
- “무료로 운영”을 노린다면 **스토어 등록비(특히 iOS)** 와 **백엔드 무료 티어 한도**를 같이 설계해야 하며, 트래픽이 늘면 **이전·과금** 계획을 세우는 것이 좋습니다.

## 7. 정리

**앱 배포 프로세스**는 한 줄로 말해 **릴리스 빌드 만들기 → 스토어에 올리기 → 메타데이터·정책 작성 → 심사/검토 → 출시**이고, **Expo**를 쓰면 빌드·제출을 **EAS**로 많이 단순화할 수 있습니다. 백엔드는 **같은 날 “앱과 함께 스토어에 올라가는 것”이 아니라**, **서비스 URL·클라우드 리소스**로 병행 운영한다고 이해하면 이후 아키텍처 설계가 수월합니다.
